## 1. 结论与交付边界

这不是一次仅检查语法或代码风格的审查。主要问题集中在：上位机内存状态、设备实际状态、命令回执、数据库记录和界面显示被当作同一件事，但它们并不具有原子性，也不总是相互证明。

本次已经提交六组可回归验证的修复，涉及十个源码及测试文件；其余设计缺口在下文明确标为未修复。**这份报告不是“所有隐患均已消除”的证明，也不是可以接入真实反应釜无人值守运行的验收结论。** README 将项目定位为 PoC、且不替代设备本体保护；下文 P0/P1 的发布判断，是以启用真实设备控制为前提，不能反过来将演示固件的占位实现描述为已经发生的现场事故。

没有合并主分支、部署服务、写入真实串口/PLC、烧录固件或修改用户生产数据库。一次性补丁传输文件和带写权限的临时 Actions 工作流已经删除；保留的回归工作流只有仓库读取权限。

审查覆盖了 Rust API、控制循环、设备适配器、安全子进程、状态恢复、鉴权、数据库及 AI 调用链、Vue HTTP/实时状态链路，并检查了 ESP32 示例、Qt 壳、部署和 OTA 脚本。重点路径采用函数级阅读与跨模块追踪；**不声称每个历史生成产物都做了逐行人工式审计**。未运行完整 Playwright 浏览器矩阵、Qt/Arduino 构建、ARM64 交叉构建、现场串口/Modbus 压测、断电注入或长期资源观测，也未完成依赖漏洞数据库扫描。

## 2. 重新建立的业务模型

ReactorOS 是反应釜边缘上位机，不是操作系统内核。用户先配置安全边界和设备模式，采集现场样本，建立工艺/批次，再通过手动、自动或 AI 辅助入口下发目标，并记录结果供下一轮推荐使用。

```text
设备/外部采样管线
  -> 数据解析与新鲜度检查
  -> RuntimeState + SQLite 样本
  -> 人工/API/工艺/集成任务/自动控制意图
  -> 权限 + 联锁 + safety guard + 限幅
  -> 设备写入/ACK
  -> 内存状态提交 + 批次/审计记录
  -> HTTP / WebSocket / HMI
```

必须成立的业务不变量应包括：急停锁定后旧控制意图不得重新生效；超时不等于命令未执行；文件写入成功不等于执行器到位；一个组件的 ACK 不等于全部目标已应用；无测量数据不得伪装成正常测量；旧请求不得清除新会话；界面必须能区分当前值、最后已知值和未知状态；进程重启不能未经现场确认消除需要人工处理的安全锁存。

现有实现已经有不少有效防线，包括联网启动口令门禁、人工/急停/故障联锁、未完成批次恢复、控制任务退出监视、危险 OTA 参数二次确认和 tar 路径校验。问题不在于“完全没有安全代码”，而在于这些防线之间仍有语义和时序空隙。

## 4. 已修复的问题（按风险排序）

### F01 · P0 · 急停吞掉设备返回的内部错误

**位置：** `src/api.rs::emergency_stop`。

**触发条件：** 设备写入在期限内完成，但返回 `Err`，例如串口/总线拒绝或断开。

**根因：** `timeout(...).await` 返回 `Result<Result<(), Error>, Elapsed>`；原实现只转换并检查外层错误，`Ok(Err(...))` 被当成成功。

**影响：** 软件急停标志已经锁定，但 API 仍可能返回 204，审计记录声称安全目标已送达；操作员看不到应当立即处理的设备写失败。

**修复：** 展平两层结果，设备错误和超时都进入现有的故障锁存、失败审计与 503 分支；保留“先锁存急停，再等待写入”的顺序。

**验证：** 显式设备错误、正常写入和超时三个用例。正常成功路径仍返回 204。**本修复不证明所有适配器的 `Ok` 都代表物理停机；R01/R04 仍然存在。**

### F02 · P0 · 极端分页参数可令整个发布进程退出

**位置：** `src/api.rs::{audit_logs,v1_history}`，关联 `Cargo.toml` 发布配置。

**触发条件：** 传入可以解析为 `usize`、但 `(page - 1) * page_size` 溢出的页码。历史查询入口无需登录；审计查询另有权限检查。

**根因：** 页码直接参与普通整数乘法；仅限制 page_size 并不能限制乘积。发布配置同时设置 `overflow-checks = true` 和 `panic = "abort"`。

**影响：** 在测试构建中可以观察到 overflow panic；按仓库发布配置，同一路径会终止整个上位机进程，而不是仅返回一次 400。该发布后果由配置和控制流推导，本次没有对真实设备运行发布二进制实施崩溃测试。

**修复：** 统一 `checked_page_offset`，使用 `checked_sub`、`checked_mul`，并校验偏移可转换为 SQLite 的 `i64`；在进入查询前返回 400。

**验证：** 两个入口的乘法溢出、64 位平台下超出 SQLite 范围的偏移，以及正常第二页。没有把“换成无符号更大类型”误当作完整修复。

### F03 · P1 · 控制循环把超时执行和 ACK 身份完全交给适配器

**位置：** `src/device.rs::write_targets_with_ack_deadline`（新增）、`src/main.rs` 自动下发路径。

**触发条件：** 适配器忽略传入期限，或返回别的请求的 ACK。Modbus 实现原本明确忽略 `_timeout`；其内部等待不应被上层假定为瞬时操作。

**根因：** 监督层只是把 timeout 参数传下去，没有独立保证 await 有界，也没有再次验证 request_id。

**影响：** 自动控制可以被一个失联/错误适配器拖住，或接受不属于当前意图的结果。

**修复：** 监督层实施独立超时并检查 ACK request_id；超时和 ID 不匹配均报告“交付状态未知”，进入已有故障锁存，不自动重试。

**验证：** 永不返回的替身适配器、错误 ID、匹配 ID、真实内部错误四种路径。**不能把取消 await 当作取消已开始的阻塞/物理写入；R02 仍需设备所有权重构。**

### F04 · P1 · 旧请求的 401 清除新登录状态

**位置：** `frontend/src/api/http.ts`。

**触发条件：** 会话 A 的请求在途，用户退出并登录 B，此时 A 的响应返回 401；或未携带认证的登录尝试失败。还包括退出后重新获得相同 token 的 A→空→A 情况。

**根因：** 原 HTTP 层看见任何 401 就调用全局登出回调，没有证明它属于当前会话；Blob 下载有独立、同样有问题的路径。

**影响：** 新会话和正在进行的工作被无关旧请求清除，形成难复现的“随机掉线”。

**修复：** 请求捕获发送时 token 与认证世代，只有仍属于当前已认证世代的 401 才触发登出；JSON/Blob 共用处理。未认证请求的 401 不清理已有会话。

**验证：** A→B、A→退出→A、未认证失败、当前会话确实过期、Blob 旧 401。这个客户端修复不等于后端令牌撤销，后者见 R06。

### F05 · P1 · 实时响应被错误解包，且 WebSocket 不同步安全状态

**位置：** `frontend/src/api/{http.ts,types.ts}`、`frontend/src/stores/live.ts`、`src/api.rs::v1_realtime_payload`。

**触发条件：** 裸实时响应本身包含 `data` 字段；或另一端触发急停/关闭自动控制后，本端继续收到 WebSocket 测量更新；同一采样被重复广播。

**根因：** HTTP 层把任何带 `data` 的对象都当成信封；WS 只更新测量字段，沿用旧 runtime；fallback 数据没有与当前可用性严格分开。

**影响：** 丢失 device_id/status 等元数据，数值在动但急停/故障标志滞后，重复时间戳挤占曲线窗口，旧测量被当作当前值。

**修复：** 仅识别带数值 code 和 data 的信封；实时响应附带同一份 runtime 快照并在 store 合并；不可用时 `latestSample` 返回 null；同时间戳样本不重复入窗。

**验证：** 裸响应、规范信封、204、不可用 fallback、WS 急停/自动/故障字段及重复样本。**这是状态收敛的一部分修复，并未解决所有跨请求乱序与开而不活的 WS，见 R09。**

### F06 · P2 · HTTP 请求及响应体可以无限等待，降级分支不一致

**位置：** `frontend/src/api/http.ts`、`frontend/src/api/index.ts`。

**触发条件：** fetch 不返回、响应头已到但 JSON/Blob body 停住，或响应体消费抛错。

**根因：** 缺少覆盖完整请求生命周期的期限和统一清理；原 allowFailure 对部分流异常没有一致降级。

**影响：** 轮询 pending 标记、按钮 busy 和下载状态可能长期不结束，妨碍恢复。

**修复：** 一个总期限覆盖 headers 和 body，连接调用方 AbortSignal，finally 清理 timer/listener，统一错误规范化和 allowFailure；不自动重试有副作用请求。普通请求 15 秒；四类会触发 AI 生成的入口显式给 90 秒，覆盖默认 3×20 秒提供商尝试及退避，避免新修复反而截断正常 AI 流程。自定义更长服务端配置仍应同步调整预算。

**验证：** fetch 悬挂、JSON body 悬挂、Blob body 悬挂、预先取消、流异常、单次 POST 不重试，以及 AI/普通轮询期限区分。

## 5. 未修复的设计缺口与发布阻断项

以下“静态确认”表示可以从当前代码路径证明结构问题，不表示已经在真实设备上测到事故。它们没有混入上述已修复清单。

### R01 · P0 · JSON 桥接把一个原子组件命令当作整套安全目标完成

**位置：** `src/device.rs::{JsonBridgeDevice::write_targets,write_targets_acknowledged,next_json_bridge_control}`；`src/api.rs::emergency_stop`。

**触发：** 电机、继电器及搅拌同时工作，急停只调用一次通用 write_targets。

**根因：** 转换函数按 motor、speed、relay、stirrer 顺序选择一个动作后立即返回；ACK 只确认这一个动作。raw write 成功只证明 control.json 已写入，缓存还会在 ACK 前更新。继电器温控默认可以关闭；通用路径又依赖新鲜 state.json，不能把专用组件 stop 的陈旧状态放行测试推广到整套急停。

**影响：** 可能只写入 motor=0，继电器和搅拌未收到停止指令，却按整套 fail-safe targets 成功记账。自动循环可能逐步收敛，但急停之后自动已经关闭，不能依赖下一轮补齐。

**方案：** 拆分 `PrimitiveCommand`、`TargetReconciliation` 与 `StopAll`。StopAll 要么是下位机原子协议能力，要么由单一调度器按设备定义的安全顺序逐项写入并分别等待 ACK/观测。不能直接连续覆盖三次 control.json：单槽邮箱会丢掉前面的命令。维护“已请求/已发送/已接受/已观测/未知”而不是一个布尔成功。

**验收：** 三执行器同时运行、桥接状态陈旧、ACK 丢失、继电器温控关闭、仅一个组件拒绝时，都不得报告全设备已安全停机。真实停机顺序与保持压力/冷却策略需要设备协议和现场负责人确认。本次未擅自假设。

### R02 · P0 · 急停与已获准旧命令之间仍有物理副作用竞态

**位置：** `src/main.rs` 最终联锁检查→设备 await；`src/api.rs` 工艺启动、AI、组件及停止入口；设备适配器。

**触发：** A 完成联锁检查后暂停，B 锁存急停并下发安全值，A 随后继续把旧目标交给设备；或者 A 的 spawn_blocking 写入在调用方超时后继续运行。

**根因：** RuntimeState 锁和 generation 检查主要保护内存提交，不拥有真实传输的全生命周期。多个入口能直接调用设备。底层互斥锁只保证串口不同时写，不保证“急停之后不能执行旧意图”的业务顺序。

**影响：** 软件状态保持急停，但物理目标仍有被旧任务覆盖的可能。事后拒绝更新内存并不能撤销已经发送的字节。

**方案：** 每台设备一个拥有传输句柄的有界 CommandDispatcher；所有入口只提交意图。携带 boot_id、safety_epoch、intent_id、deadline，真正发出前再次检查世代，急停使旧队列失效并具有独立高优先级通道。对已经执行中的阻塞传输，必须有明确终止/排空/物理联锁协议；不能用外层 mutex+timeout 宣称完成隔离。

**验收：** 用屏障强制排列“准入→急停→恢复旧任务”“写入超时→旧阻塞线程继续”“重启→旧 ACK 回来”，检查实际输出字节序列，不只检查 RuntimeState。此竞态尚未完成实机或穷举调度验证。

### R03 · P1 · Modbus 模式补造未测量字段，并过度报告已接受目标

**位置：** `src/device.rs::ModbusRtuDevice`。

**触发：** 启用 Modbus RTU，只有温度和搅拌寄存器被读取或写入。

**根因：** 样本中压力、流量、浓度、摇速等直接填 0，pH 填 7，并赋予当前时间；accepted_targets 又带上并未向设备写入的其他命令字段。

**影响：** “未知”被编码成“正常、且新鲜”，上层阈值/显示/优化无法正确解释数据；用户请求的摇速等参数可能没有物理效果。

**方案：** 为每个字段记录 validity、source、captured_at；按真实寄存器映射实现读取或明确 Unsupported/Unavailable。ACK 仅列出实际应用的字段。禁止用 0 作为通用缺失值，禁止简单比较全目标相等而忽略寄存器量化。

**验收：** 缺失寄存器、不同缩放、量化误差、部分写成功、超时与读回不一致测试；实机映射未提供，本次不编造地址。

### R04 · P1 · ACK 要求不是所有控制入口的一致契约

**位置：** `src/device.rs` trait、Pipeline 实现；`src/main.rs` 与 `src/api.rs` 多个 raw write 路径。

**触发：** 手动启动、AI 或停止路径直接 raw write；或在 Pipeline 模式下调用通用设备控制。

**根因：** 自动循环对 require_command_ack 有检查，其他入口仍依赖原始 `Result<()>`。Pipeline write 是空操作，但 acknowledged 路径能返回 Confirmed。上层对 accepted_targets 的语义校验也未闭环。

**影响：** 同样的“成功”在不同模式下可能分别指内存接受、文件落盘、总线回显或实际目标保持；用户无法判断控制是否发生。

**方案：** 统一所有入口到 R02 调度器。Pipeline 没有出站控制协议时明确标为 monitor-only；已存在外部控制器时明确建模外部命令协议和责任，不把空操作伪装成设备确认。定义 read-back/accepted/observed 的不同等级。

**验收：** 全设备模式×全控制入口契约矩阵；配置要求 ACK 时，不应存在无 ACK 的普通执行成功路径。风险降低型停止可以尽力下发，但必须呈现 unknown，而非静默拒绝或虚假确认。

### R05 · P1 · 安全子进程的期限不覆盖完整通信，存在管道阻塞和资源滞留

**位置：** `src/safety_guard.rs::evaluate_with_process`。

**触发：** 子进程不读取大量 stdin；大量写 stdout/stderr；或者子进程退出但后代仍持有管道。

**根因：** 写 stdin 在 wait_timeout 之前；等子进程退出后才读 stdout/stderr；read_to_end 没有大小和期限；部分早退路径缺少统一 kill/reap。外层 spawn_blocking 的取消不能终止已启动阻塞工作。

**影响：** 名义上的安全判定超时不是真正端到端期限，可能长期占用线程、内存或保留子进程，拖住控制判断。

**方案：** 同时异步写 stdin、有限读取两条输出流；对 spawn→写入→等待→解析实施一个总 deadline；所有错误和取消路径 kill 并 reap；为进程树和输出上限制定平台策略。

**验收：** 不读 stdin、无限 stdout、无限 stderr、无效 JSON、持管道的子孙进程、运行中取消。现有“sleep 超时”用例只覆盖其中一种，本次未完成这一跨平台重构。

### R06 · P1 · 后端口令变更、令牌撤销和长连接生命周期脱节

**位置：** `src/api_auth.rs::{prepare_password_change,authenticated_user,password_override_hash}`、`src/api.rs` 改密和实时 WS 路径、`src/bootstrap.rs`。

**触发：** 联网部署启动通过强口令门禁后，改为仅 6 字节口令；旧 token 泄露后执行改密；已连接 WS 跨过 token 有效期。

**根因：** 改密最小长度与启动门禁不一致，持久化覆盖口令不属于启动环境变量检查；口令采用快速 SHA-256 组合哈希而非专门口令 KDF；token 验证没有用户级撤销世代；WS 只在握手鉴权。并发改密的读/校验/写和审计也不是统一事务。

**影响：** 改密不保证失窃会话立即失效，长连接权限生命周期与普通请求不同；存在弱口令和审计/结果不一致风险。**不能据此说项目默认允许弱口令公开监听：联网启动防线确实存在。**

**方案：** 统一持久化口令策略和随机盐 KDF，采用标准消息认证或服务器端会话；改密事务递增用户 session_epoch，验证请求及长连接时执行撤销/到期；限制登录尝试，明确定义并发修改和审计原子性。迁移需兼容现有用户和令牌，未在本次仓促替换。

### R07 · P1 · 无未完成批次时，重启不能保留先前安全锁存

**位置：** `src/runtime_recovery.rs::recover_runtime_from_db`、`src/state.rs` 初始化。

**触发：** 设备曾因急停/故障/人工维护被锁定，但数据库中没有未完成批次，此时服务重启。

**根因：** 恢复以 unfinished_batches 为主，急停、人工锁存和故障世代没有独立持久化恢复。

**影响：** 重启后的界面和复位约束不能表达重启前需要人工确认的原因。**启动时 auto 仍然为 false，不能夸大成“重启会自动开始生产”。**

**方案：** 独立持久化 safety latch/epoch 与恢复原因，开机进入 reconciliation 状态；重新确认设备身份、状态新鲜度和执行器状态后才允许显式解除。不能用批次记录代替安全状态日志。

**验收：** 无批次急停、已结束批次后的故障、写库失败、断电及旧日志重放；需要确定项目的重启维护政策后实现。

### R08 · P1 · 急停面板有输入通道和失败反馈缺口

**位置：** `frontend/src/components/EmergencyStopPanel.vue`。

**触发：** 键盘触发按钮 click、pointercancel、多次 pointerdown，或后端已经锁存但设备写入失败返回 503。

**根因：** 未急停状态的 handleClick 直接返回，触发依赖 pointer 长按；缺少 pointercancel 和重复启动防护；失败分支 String(error) 可能显示无意义对象且不主动刷新状态。文案声称“立即停止所有操作”，实际先等待 1.5 秒且后端未证明所有设备停止。

**影响：** 键盘可聚焦但无法按预期急停，取消手势与触发行为不一致，部分成功/物理失败被显示为单一失败。

**方案：** 将“请求急停”和“复位”分离；给键盘、触屏、指针定义一致可验证行为。不能未经风险评估移除所有确认，但急停不应依赖隐藏输入方式。显示软件锁存与物理确认两个状态，失败仍刷新并显著提示现场硬件急停。必须做真实浏览器输入和焦点测试；本次仅静态确认，未将其列为已修复。

### R09 · P1 · 实时状态仍缺少跨请求排序和独立的新鲜度寿命

**位置：** `frontend/src/stores/live.ts`、`src/api.rs::v1_realtime_socket`。

**触发：** 较早 HTTP 请求晚于新 WS 帧返回；WS 连接仍显示 open 但长时间没有新数据；测量不可用时安全状态也随同 503 丢失。

**根因：** 没有 boot_id+单调 sequence 去拒绝旧快照；连接状态代替数据新鲜度；已连接时慢轮询可以到 60 秒，安全标志和测量可用性没有分离。

**影响：** F05 修复了正常新帧的状态同步，但不能保证界面从不回退到旧状态，也不能保证静默失联及时显露。

**方案：** 服务器统一发布带 boot_id/sequence 的快照；客户端只接受更新世代/序号；本地 receipt timer 和设备采样年龄分别判断；即使没有测量也返回安全/故障状态。解绑或切换会话时取消/隔离旧刷新。

**验收：** 旧 HTTP 晚到、WS 静默、断网恢复、服务器重启序号归零、多标签页和退出中刷新。使用假时钟测试，不能只依赖 happy-path WebSocket 测试。

### R10 · P2（资源受限实机可升级）· AI、历史数据和实时订阅缺少统一资源预算

**位置：** `src/api.rs::generate_recommendation`、`src/optimizer.rs::recommend_with_memory`、`src/db.rs`、实时 WS 循环。

**触发：** 批次成果持续增加、多个用户同时生成建议、很多 WS 订阅者或多年样本积累。

**根因：** 每次生成加载全部 batch outcomes，再同步克隆、排序和搜索；计算在异步工作线程上执行，主 runtime 固定只有两个 worker。每个 WS 客户端独立构造快照和查询，缺少共享广播、连接预算和明确慢消费者治理。数据库没有面向长期运行的统一保留/归档预算。

**影响：** 内存、CPU、DB 查询和响应延迟随数据/订阅规模放大，控制与管理 API 竞争执行资源。这里只给出复杂度和共享执行器风险，不捏造某型号开发板的 CPU/RSS 实测数字。

**方案：** AI 使用有界专用执行器和 semaphore；按成果版本进行 single-flight 与结果缓存；先定义保真要求再限制训练窗口/增量统计，不能任意截断历史。遥测采用单生产者快照广播、订阅限额、慢消费者断开；分别定义样本、审计和批次的保留及归档策略。不要直接删除审计链来“优化”。

**验收：** 1k/10k/100k 成果的耗时、RSS、控制循环抖动；1/10/100 订阅者 DB 查询率；磁盘空间和 WAL 增长；并发生成时急停可用性。尚未执行性能压测，因此没有提交未经语义验证的数据裁剪。

### R11 · P1 发布阻断 · 示例 ESP32 固件不能当作真实设备保护实现

**位置：** `firmware/esp32_reactor_bridge/esp32_reactor_bridge.ino`。

**触发：** 将仓库示例直接作为真实执行器固件使用。

**根因：** 测量含模拟生成，applyTargets/看门狗安全动作仍有占位内容，不能据此证明真实驱动、失联停机或完整命令 ACK 协议已经实现。

**影响：** 上位机测试和串口帧演示都通过，也不能证明电机、加热和保护机构会按要求动作。示例的存在本身不等于生产故障。

**方案：** 明确 demo-only 构建标识和设备能力握手；实现真实传感器质量、命令事务/ACK、下位机独立失联与超限保护，现场硬件保护不依赖上位机存活。

**验收：** 串口拔除、主机断电、部分帧、坏数字、重复命令、过期 request_id、执行器拒绝和本体保护触发；本次没有 Arduino/实机测试。

### R12 · P2 · OTA 完整性校验不等于发布者身份验证

**位置：** `deploy/reactor-edge-ota-lib.sh` 与 update/rollback 脚本。

**触发：** 发布包及其 SHA-256 sidecar 来自不可信分发链路，攻击者能够同时替换两者，并诱导有权限者安装。

**根因：** 摘要证明包与 sidecar 一致，不证明被信任的发布者批准；安装阶段会更新 root 使用的工具和服务文件。

**影响：** 有权限安装的恶意包可以带来高权限代码。这里不是声称一个未认证远程请求就能直接升级设备。

**方案：** 固定可信公钥验证签名 manifest，绑定设备型号、版本、包摘要、最低回滚版本；把受信安装器与待安装内容的信任关系分开，明确密钥轮换和应急恢复策略。

**已排除的误报：** 当前 tar 校验确实拒绝路径穿越和非普通文件/目录；健康检查除 HTTP 外还检查安全 idle；自动及手动回滚路径会恢复旧槽 root OTA 工具。14 个现有 OTA 门禁脚本已通过，不应把这些已实现防线报告为缺失。

## 6. 架构与维护性判断

Rust/Tokio/Axum + SQLite 在单设备边缘场景并非错误技术选型，没有证据支持为审查而改成微服务或远端数据库。更应该重构的是副作用所有权、数据质量、命令状态机和一致性边界。

建议保留单进程部署形式，将当前庞大 API/设备模块拆成应用命令服务、单设备执行器、查询投影、会话服务和独立有界优化器。HTTP、MQTT、Modbus TCP 和 UI 只能调用同一个应用命令契约，不能分别实现“近似相同”的联锁与成功定义。

数据库事务只能原子提交数据库，不能原子提交物理动作。应记录 command intent、send attempt、ack/observed result 与 unknown 状态，并使重试幂等且受世代隔离；不要在 timeout 后自动重发，也不要把“数据库回滚”当作设备回滚。

对 rusqlite/SQLx 双路径，应合并契约测试和迁移约束，而不是未经分析删除同步路径：部分同步实现用于内存测试/回退，不能概括成所有生产 SQL 都阻塞。现有审计链查询已有有界验证，不能误报为每次必然全库扫描。

文档已经发生漂移：README 仍声称前端无框架/打包器，并提到不存在的 workshop/frontend，而当前构建脚本使用 frontend/dist，实际依赖 Vue/Pinia/Vite。需要统一真实构建与设备能力文档；文档中的“所有控制安全”“命令已确认”等断言必须用契约矩阵支持。

## 7. 推荐的目标控制状态机与验收顺序

```text
Requested -> Admitted(epoch) -> Queued -> Dispatched
                                  |          |
                              Superseded   Accepted -> Observed
                                             |
                                     Rejected / Unknown

EmergencyStop:
  latch durable safety_epoch
  invalidate older queued intents
  execute device-specific StopAll through sole transport owner
  report each actuator confirmation or Unknown
  require explicit, audited recovery before ordinary admission
```

第一阶段先关闭 R01/R02/R03/R04：定义并实现整套停机、唯一设备下发者、真实字段质量和跨入口 ACK 契约。第二阶段处理 R05/R06/R07/R08/R09：通信全生命周期、会话撤销、重启锁存及界面输入/新鲜度。第三阶段用实测数据治理 R10，并完成 R11/R12 的固件与发布信任链。

放行必须包含：急停后无旧非安全命令生效；写入中断/失联均保持 unknown 或安全锁存；多执行器停机逐项证明；无新鲜测量时 UI 不显示正常当前值；改密撤销旧请求与长连接；重启不自动消除维护状态；并发 AI/导出/订阅压力下控制延迟符合设备规定；断电与 A/B 回滚后的 DB/程序/安全状态可解释。
